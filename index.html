00 / ReAct 与模型训练

训练 OPC Agent，
需要什么数据与环境？

TASK → ACTION
↑　　　　↓
FEEDBACK ← TOOL

ReAct：模型根据任务和已有结果选择动作，调用工具，观察反馈，再决定下一步。训练与评测这类能力，需要可执行的任务、真实反馈，以及明确的完成标准。

TASK任务目标、约束、初始状态
ENVIRONMENT环境文件、软件、模型、资料
ACTION动作可编辑内容、可用工具
OBSERVATION反馈运行结果、日志、诊断
EVALUATION评价验收规则、得分、终止条件
交流目标

以真实 OPC 工作为参照，确定任务包和数据采集方式。
工程师的操作记录可构成示范轨迹；可重复运行的环境与验收程序可支持模型自行探索、训练和评测。

01 / 当前实验与工作假设

我们从 Benchmark，
推测出的任务结构。

目前的信息主要来自 VPEvolve 及我们的实验适配。以下是当前实验配置，不能直接视为工厂的标准工作流。

要素当前实验中有什么
输入与环境GDS、选定图层与局部窗口、初始 recipe、固定研究工艺模型、Calibre。
任务与动作在给定约束下改善结果；修改 recipe、运行工具、查看输出，再进行下一轮调整。
反馈与评价轮廓、热点、EPE / PVB 等指标及规则检查；与基线比较，判断候选是否可保留。

需要对齐：真实任务是否也能这样拆解？差异可能在版图规模、工艺模型、操作范围、工具反馈和验收要求，需要用实际任务逐项确认。

下一步不是直接扩展 benchmark，而是拿到实际任务的组成和执行过程，据此构造数据。

02 / Task + Workspace

一条真实任务，
从什么状态开始？

类比 coding：任务描述 + git / workspace + 依赖环境。OPC 中需要对应到具体文件和配置。

A

任务如何提出，具体要解决什么？

开发一套 recipe、修复一类热点、适配新设计，还是完成某个图层的 OPC？一次任务的范围和目标如何描述？

B

初始目录中有哪些文件？

完整芯片、指定图层或局部图形？是否附带 target、初始 recipe、工艺模型、已有结果、运行脚本和参考资料？

C

哪些条件固定，哪些属于优化对象？

工具及版本、模型及校准状态、测量方式和规则检查由谁确定？哪些内容允许 OPC 工程师调整？

对应数据：任务描述、初始文件快照、依赖与版本、固定项和可修改项。

03 / Action + Tools

模型应当能做哪些动作，
通过哪些接口执行？

类比 coding：编辑文件、执行 command、调用 tools。需要保留工程师实际可用的操作能力。

A

优化动作的实际范围是什么？

调 recipe 参数、改分段策略、写图形相关规则、移动局部边缘、调整 SRAF，分别通过什么方式完成？

B

哪些工具可以脚本化，哪些依赖 GUI？

使用哪些 Calibre 产品或其他软件？命令、输入输出格式、参数说明和错误诊断是否有完整文档与示例？

C

工程师做决策时还依赖什么信息？

手册、历史案例、内部规则、可视化和经验判断，哪些可以成为模型可读取的上下文或检索资料？

对应数据：工具接口、命令示例、可编辑文件、操作文档，以及实际使用的参考资料。

04 / Action → Observation → Next Action

一次工程迭代，
怎样记录为训练数据？

只保存最终 recipe，无法还原“遇到了什么问题、做了什么修改、结果怎样”。需要把动作与反馈对应起来。

A

每轮实际看哪些结果？

汇总指标之外，是否查看轮廓、误差坐标、违规类型、局部图形、日志及不同工艺条件下的结果？

B

修改与运行过程能否完整保留？

保存文件差异、工具命令与参数、输出文件、指标、耗时，以及候选被保留或回退的结论；同时保留失败尝试。

C

局部实验与全图层验证怎样衔接？

工程师何时选热点、改通用规则、跑回归或全图层？能否从一个真实案例还原完整的决策顺序？

对应数据：初始状态 → 修改 / 调用 → 真实输出 → 指标与工程判断 → 下一轮，直到任务结束。

05 / Evaluation + Reward

怎样把工程验收，
变成可计算的反馈？

先明确工业上的合格标准，再设计训练得分。不能仅凭一个局部指标下降，就判断任务完成。

需要明确讨论内容
优化目标EPE、CD、工艺窗口、PVB、运行成本等如何排序？最坏点、违规数量与整体统计怎样取舍？
硬约束哪些掩模规则、SRAF 打印问题、工艺条件或其他退化不可接受？如何自动检查？
完成条件需要达到什么阈值、通过哪些回归？何时必须做全图层检查，何时还需晶圆测量或人工确认？

哪些判断可以写成程序，哪些仍需工程师判定？模型误差、仿真不稳定、运行失败、预算耗尽和任务未完成，应分别怎样记录与评价？

对应数据：验收程序或规则、基线结果、候选得分、失败原因，以及必要的人工标签。

06 / 任务分布与独立评测

哪些任务与图形，
才有代表性？

训练要覆盖真实工作中的问题，评测要检查模型能否处理未见过的任务，而不只是记住已有案例。

A

真实工作主要由哪些任务构成？

不同图层、工艺、设计、热点类型和任务阶段，各自常见的难点是什么？哪些环节最耗人工和经验？

B

局部数据需要保留多大上下文？

裁剪窗口、邻近图形、密度和边界怎样影响结果？局部修正如何验证能推广到相似图形和整个图层？

C

怎样安排训练集、回归集与独立测试集？

按设计、图形族或工艺划分是否更合理？实际有哪些历史案例和未参与调参的设计可用于验证？

对应数据：代表性任务集合、图形上下文、回归样本和独立测试任务，而非单个成功热点。

07 / 从真实任务构造数据

先用一个真实任务，
把数据与环境对应起来。

讨论哪些材料已有留存、哪些可以脱敏提供、哪些需要在后续执行中补充采集。

任务与输入
具体目标、初始 GDS / 图层 / 窗口、recipe、工艺模型或等价可调用环境。
执行环境
软件与版本、运行入口、工具接口、依赖配置、实际使用的手册或参考案例。
过程与结果
逐轮修改、命令、输出、指标和保留 / 回退结论；包含失败尝试及最终交付物。
验收与测试
基线、硬约束、完成标准、回归集，以及可独立验证的新增任务。

据此构造：可运行任务 + 工程师示范轨迹 + 可验证反馈。先完成一个任务的重放与验收，再扩展任务类型和数据规模。
